# M1 and M2: the database key and the backup passphrase

Owed from the Phase 1 whole-branch review (2026-11-23). The owner chose on 2026-11-24 to fix M1 and the
no-screen part of M2 now; the passphrase-change screen, its wording and the "fresh backups at once" step
of R109 wait for the settings work.

- **M1.** The database key is derived from the passphrase (`MedicAllCore.databaseKey`), so a passphrase
  change cannot leave it right, and it ties the database to the passphrase for no gain.
- **M2.** Backups take whatever passphrase the caller gives, and a passphrase change made on another
  device is not noticed: this device would go on writing backups under the old passphrase.

One branch (`m1-m2-keys`), one PR, squash-merged. Inline mode, an independent review of the whole diff
before the PR. Rules touched: R10, R109.

## Task 1 — M1: a random database key, kept only in the key store

Files: `data/.../MedicAllCore.kt`, `android/.../KeyVault.kt`, `data/src/androidMain/.../EncryptedDatabase.android.kt`,
`android/src/debug/.../HarnessActivity.kt`, tests.

1. Tests:
   - `MedicAllCoreTest.databaseKeyIsRandom_SPEC_R10`: `MedicAllCore.newDatabaseKey()` gives 32 bytes, two calls differ.
     Fails: no such function.
   - `EncryptedDatabaseTest.databaseKeyIsMadeOnceAndKept_SPEC_R10` (instrumented): `KeyVault.databaseKey()` on an
     empty vault returns `isNew = true`; a second vault over the same files returns the same bytes with `isNew = false`.
   - `EncryptedDatabaseTest.newKeySetsTheOldDatabaseAside_SPEC_R10` (instrumented): a database written under key A,
     opened with key B and `setAsideExisting = true`, opens empty with `recovered = true`, and the old file is
     kept beside it (set aside, not deleted).
2. Code:
   - `MedicAllCore.newDatabaseKey(): ByteArray` (32 bytes from the secure random source); `databaseKey(passphrase, device)` removed.
   - `KeyVault.databaseKey(): DatabaseKey` with `class DatabaseKey(val bytes: ByteArray, val isNew: Boolean)`: the stored
     key, or a new one stored at once.
   - `openEncryptedDatabase(context, key, name, setAsideExisting: Boolean = false)`: when true and a database file
     exists, it is set aside first (`setAsideDatabaseFiles`) and the result says `recovered = true`, so the sync
     reads every peer's log again and the database is rebuilt from the folder.
   - Harness: the database opens with `vault.databaseKey()`, before and apart from the passphrase.
3. SPEC R10 Evidence: the key is 32 random bytes kept only in the key store, never derived from the passphrase; a lost
   key sets the database aside and it is rebuilt from the sync folder and the backups. History row.

## Task 2 — M2: backups use the passphrase that unlocked sync

Files: `data/.../MedicAllCore.kt`, `HarnessActivity.kt`, `MedicAllCoreTest.kt`.

1. Tests (`MedicAllCoreTest`):
   - `openRefusesAWrongPassphrase_SPEC_R109`: `MedicAllCore.open` with another passphrase gives
     `Opened.Refused(Unlock.WrongPassphrase)`.
   - `backupUsesThePassphraseThatUnlockedSync_SPEC_R109`: `backUp(target)` takes no passphrase; the backup restores
     with the passphrase that opened the core, and not with another.
   - `peerPassphraseChangeIsNoticed_SPEC_R109`: B changes the passphrase (`KeyFolder.change`, as the owed flow will);
     A's next `syncNow` says `unlockAgain`; A's `backUp` then returns `Failed` naming the change and writes nothing;
     opening A again with the old passphrase is refused, with the new one it is `Ready` and backs up under the new one.
2. Code:
   - `MedicAllCore.open(db, folder, device, passphrase, blobStore, workDir, …): Opened`, with
     `sealed interface Opened { class Ready(val core: MedicAllCore, val unreadableKeyIds: List<String>); class Refused(val reason: Unlock) }`.
     It unlocks (`unlockOrCreate`) and keeps its own copy of the passphrase; `close()` clears it.
   - `backUp(target, kind)` and `checkFiles(target)` use that copy. `backUp` returns
     `Failed(PASSPHRASE_CHANGED)` while the folder's current key is not the one this core opened.
   - `restoreBackup(target, passphrase = the kept one)`: a person may give an older passphrase for an older backup.
   - Harness: opens the core from the passphrase; on `unlockAgain` it opens again with the kept passphrase and, when
     that is refused, asks for the current one.
3. SPEC R109 Evidence: backups are sealed with the passphrase that opened the sync key; after a change on another
   device this device writes no backup until it is given the new passphrase. History row.
